## 1. System Overview

Deendoon is a multi-tenant **Smart Debt Recovery / Collection Management** SaaS backend. Each tenant is a business (SME) tracking its own customers, the debts those customers owe, and the recovery workflow (reminders, promises to pay, collection cases, professional/third-party collection escalation, payments, and generated documents) used to recover them.

**Actual tech stack (verified from code, not assumed from SRS):**

| Layer | Technology | Verified from |
|---|---|---|
| Framework | Laravel 13 (PHP ^8.3) | `composer.json` |
| Database | **PostgreSQL** (`pgsql`) | `.env` `DB_CONNECTION=pgsql`, `config/database.php` |
| Auth | Laravel Sanctum ^4.0, Bearer-token mode (not cookie/SPA mode) | `config/sanctum.php`, `AuthController` |
| Authorization | spatie/laravel-permission ^8.3 — **roles only, permissions installed but unused** | see §6 |
| Queue | `database` driver | `.env` `QUEUE_CONNECTION=database` — **no queued jobs exist anywhere in the app** (0 `ShouldQueue` usages); see §11 |
| Cache | `database` driver | `.env` `CACHE_STORE=database` — **no Redis**, despite the original SRS tech stack naming Redis |
| Session | `database` driver | `.env` |
| PDF generation | barryvdh/laravel-dompdf ^3.1 | `composer.json`, `DocumentService` |
| Excel import/export | maatwebsite/excel ^3.1 | `composer.json`, `CustomerImportController`, `ReportExportService` |
| Mobile client | Flutter (Dio + Riverpod, Clean Architecture) | `mobile/` |
| Web admin client | **None found in this repository** | see [Backend_Audit_Report.md](./Backend_Audit_Report.md) §1 |

**Multi-tenancy model:** one row per tenant in `tenants`; every tenant-owned table carries a `tenant_id` (char(26), ULID-shaped) and is isolated at the **application layer only** — no PostgreSQL Row-Level Security is adopted (a deliberate, documented Product Owner decision — see §6.4). There is no tenant-aware HTTP routing (no subdomain/path tenant prefix) — tenant identity is resolved entirely from the authenticated user's `tenant_id`.

**ID strategy (mixed, deliberately, permanently):** every domain table uses a `char(26)` ULID primary key generated by the application (`HasUlids`), **except `users.id`, which remains a Laravel-native `bigint`**. This is an accepted, permanent architectural decision (`docs/Database_Architecture.md`), not a migration-in-progress — see §4.11 for its consequences.

## 3. Layered Architecture

```
HTTP Request
   │
   ▼
Route (routes/api.php)  ──── all under auth:sanctum except register/login/forgot-password/reset-password
   │
   ▼
FormRequest (validation only — every authorize() returns true; authorization is NOT done here)
   │
   ▼
Controller (thin — resolves the model via route-model-binding, calls $this->authorize()/Gate::authorize(),
            delegates business logic to a Service, wraps the result in an API Resource)
   │
   ├──▶ Policy / Gate   (role-based authorization — see §6)
   │
   ▼
Service (the business-logic layer — DB transactions, cross-model orchestration, audit logging,
         notification dispatch, document generation)
   │
   ▼
Eloquent Model (BelongsToTenant global scope auto-applies WHERE tenant_id = ? on every query)
   │
   ▼
PostgreSQL
```

This layering is a **Product Owner-accepted architectural decision** (`docs/Engineering_Excellence.md`, Sprint 4.1 audit) — verified consistently applied across every Service/Controller/FormRequest/Resource in the codebase, with exactly one documented exception (`CustomerImportController` still has business logic in the controller — an approved-but-not-yet-implemented future extraction into an `ImportService`).

**Response envelope** (via `App\Traits\ApiResponse`, used by every controller): every response, success or failure, is
```json
{ "success": bool, "message": string, "data": mixed|null, "errors": object|null }
```
Validation errors (422), auth failures (401), authorization failures (403), and rate-limit failures (429) are all normalized onto this same shape by handlers registered in `bootstrap/app.php` — not Laravel's default JSON error shape.

## 4. Database Schema

Full detail (33 migrations, chronological). PostgreSQL only — CHECK constraints below are guarded by `DB::connection()->getDriverName() === 'pgsql'` and are silently absent under SQLite (the test suite's driver), where enforcement falls back to Form Request validation alone.

### 4.1 ID & timestamp conventions
- **Laravel-native tables** (`users`, `sessions`, `jobs`, `personal_access_tokens`, all spatie permission tables): `bigint` auto-increment PK, ordinary `timestamp` columns.
- **Every domain table** (`tenants` downward): `char(26)` ULID PK generated by the app, `timestampTz` columns (`useCurrent()` default).
- **No FK to `users.id` exists anywhere in the schema** — see §4.11.

### 4.2 Core tenancy & auth tables

| `password_reset_tokens` | Stock Laravel table, PK is `email` | No tenant scoping (pre-auth flow). |

| `personal_access_tokens` | Sanctum | Unmodified stock shape; `last_used_at` is the column `EnsureTokenIsNotIdle` reads (§7). |

### 4.9 Performance indexing

`2026_08_04_090000_add_performance_indexes.php` (Phase 13) retroactively added three indexes that were gaps against the project's own "every FK must be backed by an index" rule: `import_rows.resulting_customer_id`, `statements.debt_id`, and the `notifications` dedup-lookup composite index. Treat any **new** FK column added in future work as needing its own explicit index — PostgreSQL does not auto-index FK columns, and this project has already been bitten by forgetting it twice.

### 4.10 Accepted, permanent schema decisions (do not "fix" these without a new Product Owner decision)

1. **`users.id` stays `bigint`; no FK from actor columns to it.** (`docs/Database_Architecture.md`, Decision 1 — permanent, not a migration backlog item.)
2. **`system_settings.professional_collection_threshold_days` and `soft_limit_warning_threshold` have no CHECK constraint**, deliberately deferred until the automation that consumes them is built (`docs/Database_Architecture.md`, Decision 2).
3. **PostgreSQL Row-Level Security is not adopted for V1** — application-layer isolation only (§6.4).

### 4.11 Known schema anomalies to verify before extending

- **`follow_up_history.collection_case_id` was promised an FK "once the target table exists" — it never got one.** `collection_cases` now exists (created after `follow_up_history`); the FK was never added in any subsequent migration. Any future migration touching this table should close this gap.
- **`reminders.related_case_id` and `sent_messages.case_id` both declare an FK to `collection_cases.id` in migrations dated *before* `collection_cases` was created** (2026-07-27 vs. 2026-07-31 by filename timestamp). This should be verified against the actual migration run history in a real environment — either the deployed run order differs from filename order, or this is a real ordering defect that only "works" because SQLite (the test DB) doesn't enforce FK target existence at migration time.
- **`ProfessionalCollectionRequest` deliberately does not use `BelongsToTenant`** despite having a `tenant_id` column and FK — its bimodal visibility (submitting tenant + cross-tenant Platform Administrator) is hand-scoped in its Controller/Policy instead. Any new query against this model must replicate that manual scoping — there is no ORM safety net here.
- **`AuditLog` and `User` both hold `tenant_id` but are not scoped by `BelongsToTenant`, with no docblock explaining why** (unlike `ProfessionalCollectionRequest`/`ImportRow`/`RequestMessage`, which all have explicit "deliberately does not..." docblocks). Flagged in the Audit Report as a verification item, not a confirmed-safe design choice.

## 5. Models

26 Eloquent models in `app/Models/` (+ `Concerns/BelongsToTenant.php`). Conventions used **throughout, no exceptions**:
- Mass assignment via PHP 8 attribute `#[Fillable([...])]`, never `protected $fillable` or `$guarded`.
- Casts via `protected function casts(): array` method style, never a `$casts` property.
- **No model defines a local query scope** (`scopeXxx()`).
- Money fields are always `decimal` casts, compared with `bccomp`/added with `bcadd`/`bcsub` — never floating-point arithmetic.

### 5.1 `BelongsToTenant` trait — the tenancy enforcement mechanism

Two responsibilities, both via Eloquent's `bootBelongsToTenant()` convention:
1. **Global scope**: appends `WHERE tenant_id = ?` to every query, where `?` is `Auth::guard('sanctum')->user()->tenant_id`. **Fails closed** for a null-tenant actor (the Platform Administrator) — the scope becomes `WHERE tenant_id IS NULL`, correctly returning zero tenant rows rather than becoming a no-op.
2. **Auto-fill on create**: a `creating()` hook sets `tenant_id` from the authenticated user if not already set. This is the *only* path `tenant_id` is ever set — it is never in any model's `Fillable` list.

### 5.2 Models WITH `BelongsToTenant` (19)
`ImportBatch`, `FollowUpHistory`, `PromiseToPay`, `CollectionCase`, `DocumentEvent`, `Payment`, `Customer`, `Notification`, `SystemSetting`, `DocumentTemplate`, `ReferenceData`, `MessageTemplate`, `SentMessage`, `Reminder`, `Receipt`, `DemandLetter`, `Statement`, `Invoice`, `Debt`.

### 5.3 Models WITHOUT `BelongsToTenant` (7) — reason for each

| Model | Reason | Risk level |
|---|---|---|
| `Tenant` | Is the tenancy root itself | None |
| `ImportRow` | No `tenant_id` column; scoped relationally through `ImportBatch` (documented) | Low, if never queried directly outside its parent |
| `ProfessionalCollectionRequest` | Bimodal visibility (tenant + cross-tenant admin); hand-scoped in Controller/Policy (documented) | Medium — no ORM safety net for future queries |
| `RequestMessage` | No `tenant_id` column; scoped relationally through parent Request (documented) | Low, same caveat as ImportRow |
| `AuditLog` | **Not documented** — holds `tenant_id` directly and it's even Fillable | **Flag for verification** |
| `User` | **Not documented** — is the tenancy boundary itself, but has a real `tenant_id` | **Highest risk of the unscoped set** — every `User` query (admin listings, policies) must manually filter by tenant; verified today that `AdminUserController::index()` does (`User::where('tenant_id', ...)`), but this is not structurally enforced |
| `PasswordResetToken` | No `tenant_id` column; pre-auth flow, inherently cross-tenant | None |

### 5.4 Notable model-level business logic (the exceptions to "plain relationships/accessors")

- **`Customer::remainingCredit()`** — the one true computed accessor: `bcsub(credit_limit, outstanding_balance, 2)`, never clamped to zero (BRL-017).
- **`User::booted()`** — on `restoring`, sets `status = 'active'`; overrides `runSoftDelete()` to set `status = 'archived'` atomically alongside `archived_at` (Archive/Restore pattern, not stock `SoftDeletes` behavior).
- **`AuditLog`, `DocumentEvent`, `SentMessage`, `Receipt`, `DemandLetter`, `Statement`, `Invoice`** — all override `update()`/`delete()` to throw `LogicException`, structurally enforcing immutability rather than relying on convention alone.
- **`ReminderType` enum** (not the model) carries `carriesAmountDue()` and `label()` — business logic lives on the enum, not the `Reminder` model.

## 6. Authorization Model

### 6.1 Policies (11, one per protected model)

All registered **explicitly** via `Gate::policy()` in `AppServiceProvider::boot()` (11 calls, matching the 11 files 1:1) — this project does **not** rely on Laravel's naming-convention auto-discovery, even though it would likely work.

| Policy | Roles checked | Tenant check location |
|---|---|---|
| `CustomerPolicy`, `DebtPolicy`, `CollectionCasePolicy`, `ReceiptPolicy`, `DemandLetterPolicy`, `StatementPolicy`, `InvoicePolicy` | `admin`, `sales_finance` (role-only) | None in-policy — relies entirely on the model's `BelongsToTenant` global scope having already excluded other tenants |
| `ReminderPolicy` | `admin`, `sales_finance`, `collection_officer` (viewing); creator-or-manager for edit/delete | Same as above |
| `NotificationPolicy` | None — pure ownership (`recipient_user_id === $user->id`) | N/A |
| `UserPolicy` | `admin` only | **Explicit, repeated in-policy check** (`$user->tenant_id === $target->tenant_id`) — the only policy that can't lean on a model global scope, since `User` has none |
| `ProfessionalCollectionRequestPolicy` | `admin`/`sales_finance` (submit) vs. `deendoon_platform_administrator` only (transitionStatus/close) | Hand-written bimodal check (`isPlatformAdmin()` / `isTenantActor()`) |

### 6.2 Roles & Permissions

**Only roles are used — spatie's `Permission` model is installed (migration + config present) but has zero references anywhere in application code.** `Gate::policy` and hand-rolled `Gate::define()` closures do all authorization; no `->hasPermissionTo()` call exists.

Five seeded roles (`RoleSeeder`, idempotent `firstOrCreate`): `admin`, `sales_finance`, `customer` (no backend-actor meaning — granted no abilities anywhere), `collection_officer`, `deendoon_platform_administrator` (never assignable via the admin UI's role endpoint — excluded from its whitelist by design; always paired with `tenant_id === null`).

Four raw `Gate::define()` closures in `AppServiceProvider` for endpoints with no dedicated model: `admin-only`, `sales-finance-only`, `customer-only`, `view-reports` (admin+sales_finance), `view-dashboard` (admin+sales_finance, OR platform admin).

**No route-level role/permission middleware** (`middleware('role:...')`) is used anywhere — every check happens inside a Controller via `$this->authorize()`/`Gate::authorize()`.

`AdminUserController::updateRole()` → `UserPolicy::assignRole` (admin, same-tenant) → `AssignUserRoleRequest` validates against a **hardcoded** 4-role whitelist (never `deendoon_platform_administrator`) → `AdminUserService::assignRole()` calls `syncRoles([$role])` (single-role replacement, not additive) → revokes **all** Sanctum tokens → audit-logs `role_changed`.

### 6.3 Authentication

- **Sanctum, Bearer-token mode** (not cookie/SPA) — matches the Flutter mobile client. `config('sanctum.expiration')` is deliberately `null`; expiry is handled entirely by a custom sliding-idle-timeout middleware instead (below).
- **`EnsureTokenIsNotIdle`** — reads `personal_access_tokens.last_used_at`; if older than `SANCTUM_IDLE_TIMEOUT` (default 60 min), deletes the token and returns 401. "Sliding" because every authenticated request lets Sanctum's own guard refresh `last_used_at`. **Must be (and is) `prepend()`-ed to the global middleware stack**, ahead of the `api` rate limiter — that limiter itself calls `$request->user()`, which would silently refresh `last_used_at` first if this middleware ran later, defeating the idle check entirely.
- **Token lifecycle** — a token is only ever really deleted (never soft-expired): on idle timeout, logout (current token only), password reset success (all tokens), role change (all tokens), account deactivation (all tokens).
- **Password hashing**: Argon2id (`config/hashing.php`), min 12 chars, no composition rules; single-hash via the `'hashed'` Eloquent cast (no service ever calls `Hash::make()` before assignment — guards against double-hashing).
- **CORS**: scoped to `api/*` + `sanctum/csrf-cookie`; `allowed_origins` empty by default, env-driven (`CORS_ALLOWED_ORIGINS`); `supports_credentials: false` (Bearer-token auth doesn't need cookie credentials).

### 6.4 Tenant Isolation — the four controls in place of PostgreSQL RLS

PostgreSQL RLS is a **documented, deliberate non-adoption for V1** (`docs/Tenant_Isolation.md`). Compensating controls:
1. `BelongsToTenant` global scope (§5.1) — fails closed for null-tenant actors.
2. Policies (§6.1) — role authorization on top of the tenant scope.
3. `tenant_id` is always server-resolved from the authenticated session, never accepted from client input.
4. **Authorization masking** — a cross-tenant resource access returns 404, never 403, everywhere, so a probe can't distinguish "doesn't exist" from "exists but isn't yours."

The accepted compensating control in lieu of RLS is a **process** control (mandatory code-review checklist item for tenant scoping on every new query), not a technical second layer — a single missed `tenant_id` filter has no database-level safety net today.

### 6.5 Security event logging (two separate channels, deliberately)

- **`audit_log`** (DB, immutable) — approved business events only (the 19-value CHECK-constrained catalog): `login`, `logout`, `created`, `edited`, `role_changed`, etc.
- **`security` log channel** (file, `storage/logs/security.log`) — events with no approved `audit_log` slot: `login_failed`, `password_reset_requested`, `token_revoked_idle`, `permission_denied` (the last one logged centrally from the `AccessDeniedHttpException` handler in `bootstrap/app.php`, not per-controller).

## 7. Middleware

| Middleware | Registered | Purpose |
|---|---|---|
| `EnsureTokenIsNotIdle` | `$middleware->prepend(...)` in `bootstrap/app.php` — global, first in the stack | Sliding Sanctum idle-timeout (§6.3) |
| `SecurityHeaders` | `$middleware->append(...)` — global | `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, and (only on authenticated responses) `Cache-Control: no-store, private` |
| `throttleApi()` | Built-in, registered in `bootstrap/app.php` | Applies the `api` rate limiter (defined in `AppServiceProvider`) — env-configurable via `API_RATE_LIMIT_PER_MINUTE` (default 60/min), keyed by user id if authenticated else IP |
| Route-level `throttle:login`/`throttle:register`/`throttle:forgot-password`/`throttle:reset-password` | Declared inline in `routes/api.php` | 5/min, keyed by lowercased-trimmed-email + IP (or IP alone for register) |

No `TrustProxies` configuration is hardcoded — opt-in only via `TRUSTED_PROXIES` env var (unset = trust nothing). **This must be set correctly in any real deployment behind a load balancer/reverse proxy**, or every IP-keyed rate limiter above silently rate-limits the proxy's IP instead of the real client.

## 9. Domain Events, Listeners, Scheduled Commands

- **Dispatched events (2, both synchronous, neither queued):** `CreditLimitReached` (from `CustomerBalanceService::recalculate()`) → `CreateCreditLimitReachedNotification` listener (fans out to every admin/sales_finance user in the tenant). `PromiseBroken` (from `PromiseToPayService`) → `AdvanceRecoveryStageOnBrokenPromise` listener (Stage 4).
- **Every other "event" in this system is a recorded occurrence** (an `audit_log`/`follow_up_history` row), not a dispatchable class — see `docs/Domain_Events.md` (the project's own living catalog, cross-checked and found accurate against code during this reference's compilation) for the full 30+-event catalog mapped to FR numbers.
- **`FireDueReminders` (`reminders:fire-due`)** — the one scheduled-job-shaped command in the codebase. **Not registered in any scheduler** — no `Schedule::command()` call exists anywhere, and there is no `app/Console/Kernel.php` at all in this Laravel 13 app. It is meant to be invoked by an external cron entry once approved, per the accepted "no queue/Redis/Horizon/scheduler" architecture decision (`docs/Performance_Architecture.md`). It only fires the **in-app** delivery method — WhatsApp/SMS/Push firing unattended is out of scope.

## 10. Conventions To Follow For New Backend Work

1. **New tenant-owned table/model → use `BelongsToTenant`.** If a genuine exception is needed (bimodal visibility, relational-only scoping), document the reason in the model's docblock the same way `ProfessionalCollectionRequest`/`ImportRow`/`RequestMessage` already do — don't leave it unexplained the way `AuditLog`/`User` currently are.
2. **New FK column → add its own index in the same migration.** PostgreSQL never auto-indexes FKs; this project has already had to retroactively patch two forgotten instances.
3. **New enum-shaped column → add both a DB CHECK constraint (pgsql-guarded) and an `App\Enums` backed string enum**, mirroring the existing 11 enums 1:1 with their CHECK constraints. Don't accept free-text where a fixed value set is intended.
4. **New business logic → a Service, never a Controller.** Controllers stay thin: resolve model, authorize, call service, wrap in Resource.
5. **New protected model → a Policy, registered explicitly in `AppServiceProvider::boot()`.** Don't rely on naming-convention auto-discovery even though it would work — this project deliberately doesn't.
6. **Money → always `decimal` cast + `bcmath` functions.** Never floating-point arithmetic on currency.
7. **Immutable-after-creation records (documents, sent messages, audit rows) → override `update()`/`delete()` to throw**, matching the existing pattern, rather than relying on "nothing calls update" as an informal convention.
8. **Cross-tenant access → 404, never 403.** Preserve the masking convention everywhere.
9. **Do not introduce queue/Redis/scheduled-job infrastructure as a default choice.** The synchronous architecture is an explicit, evidence-based Product Owner decision (`docs/Performance_Architecture.md`), not an oversight. A future feature that genuinely needs it (real SMS/WhatsApp delivery, background import processing) should get its own explicit approval, not inherit infrastructure opportunistically.
10. **Before adding a new endpoint, check `docs/Domain_Events.md` and this document's §9** for whether the "event" it represents already has an approved enum slot (`audit_log.action`, `follow_up_history.action_type`, `notifications.type`) — this codebase's strong convention is to reuse an existing generic value with a descriptive `reason` string rather than inventing a new enum value ad hoc.

### 11.1 Two coexisting specification layers — important context for future work

This backend was built against **two specification sources that arrived at different times**:
1. The original 11-document SRS (`SRS/01`–`11`) — 76 FRs, ~65 endpoints, 22 tables, targeting PostgreSQL + Redis + a React admin dashboard + Flutter mobile app.
2. A later **frozen Mobile UI spec** (`Mobile_UI_V1_Frozen.md`) that drove a "Backend v2.1" pass — adding the Reminder Center (a genuinely new schedulable entity, distinct from the original FR-030 manual reminders, which still exist unchanged as `ReminderController`), polymorphic Documents endpoints, Calendar, Search, and Message Templates.

**Practical consequence for future backend work:** there are two reminder-shaped things in this codebase on purpose (`ReminderController` = FR-030 manual log actions; `ReminderCenterController` = the new schedulable `reminders` table) — this is documented in both controllers' docblocks as deliberate, not duplicate logic to be merged. Don't "clean this up" without re-reading both docblocks first.
